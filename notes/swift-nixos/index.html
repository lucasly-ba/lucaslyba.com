Building Swift from source on NixOS

NixOS breaks almost every assumption a build system makes about a Linux toolchain — and Swift's is one of the trickiest there is. Here's how the whole stack ended up building from source, reproducibly, in a single flake.nix.

Repo & full README ↗ Project page →

The premise

On a normal Linux distro, libc headers sit in /usr/include, libraries resolve transitively, and a compiler can mostly find its own runtime. On NixOS none of that is true: /usr/include is empty, nixpkgs forces non-transitive DT_RUNPATH instead of DT_RPATH, and every tool only knows the exact store paths it was wrapped with. Swift's build assumes the opposite at almost every step. The goal was a single flake that builds the compiler, standard library, C++ interop and Foundation from source — with no edits to the Swift or LLVM trees.

The cascade

Each bug unblocked the next. A few that stand out:

  • #include_next <math.h> not found — putting glibc.dev in buildInputs front-loaded glibc into the include path; clang's de-dup then dropped the cc-wrapper's correctly-placed copy, so libstdc++'s <cmath> couldn't reach glibc. Fix: don't add it — let the wrapper place it.
  • The unwrapped clang that compiles the stdlib knows no NixOS paths. Delivered glibc + libstdc++ via CCC_OVERRIDE_OPTIONS (--gcc-install-dir, -B <glibc>, -idirafter) — crucially not through CPLUS_INCLUDE_PATH, which -nostdinc++ doesn't suppress and which leaked gcc's headers into compiler-rt's sanitizers.
  • DT_RUNPATH vs transitive rpath — built a complete bootstrap runtime so the just-built swift-frontend can load libdispatch.so at runtime.
  • The stdlib's clang-importer can't find libc — it detects libc via the sysroot's system includes, so I built a glibc sysroot and passed it as -sdk.
  • C++ interop (CxxStdlib) — a link-vs-compile conflict over glibc's libc.so linker script, fixed with a symlink farm mirroring the glibc store dir under the sysroot at its own absolute path, plus delivering libstdc++ via --gcc-toolchain rather than the sysroot (two file identities → redefinition errors otherwise).

The 30-minute "hang"

Building Foundation from source, the compiler appeared to hang for over half an hour in the FoundationMacros step. A gdb backtrace — pulling the frontend's stack off a worker thread — showed it wasn't the type checker at all: it was the SIL verifier, running while the compiler rebuilt swift-syntax from its .swiftinterface. The root cause: the host swift-syntax modules were compiled by the bootstrap Swift 5.10.1, so the 6.5-dev compiler can't load them and rebuilds from the interface — which then breaks five different ways on NixOS.

The fix delivers four flags to the corelibs only (never the compiler or stdlib) plus an augmented sysroot built in the shell hook: skip the assert-only SIL verifier, give the interface rebuild a sysroot so it can find SwiftGlibc, and point ld at the gcc and runtime libs so the indirect libstdc++ / libswiftSynchronization NEEDEDs resolve.

Net result: from a clean dev shell, dobuild.sh exits 0 building compiler + stdlib + C++ interop + libdispatch + Foundation — and the test suite runs (Parse 252/252, Interpreter 257/260) with zero edits to the Swift or LLVM trees. The full per-fix breakdown, with inline flake comments and one commit per fix, is in the repo README.
