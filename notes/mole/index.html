Mole: when the map is text

Mole lets you drive the mouse from the keyboard on Linux/X11: press a key, every word on screen gets a short hint, type one, the pointer teleports there. The interesting story isn't the idea — it's the design pivot and the systems plumbing underneath.

The shape of the problem

The goal is simple to state: press a key, get two-letter labels over the screen, type a label, the pointer goes there. The hard parts are all systems: what do you point at and how do you find it; how do you draw on top of everything; how do you move and click the real pointer; and how do you make it feel instant.

The pivot: text is the map

The first design hinted clickable widgets, found through the AT-SPI accessibility tree, with OCR only as a fallback. That was abandoned — for two reasons. First, the accessibility tree only knows about controls an app chooses to declare, so huge swaths of the screen (document text, terminals, Electron apps, anything custom-drawn) were invisible to it. Second, maintaining two very different detection paths doubled the surface area for something the OCR path already covered. So Mole hints text, found by reading the screen with OCR. The accessibility tree went away entirely.

The pipeline

Everything is wrapped in a daemon so a trigger only does the per-interaction work, and the architecture is a pipeline with each stage in its own module so it can be read and tested alone:

  • capture the screen, then detect words with OCR;
  • label each target with a short hint and render them into a borderless, transparent X11 overlay the window manager won't touch;
  • match the keys you type against the labels, then act — synthetic input the rest of the system believes is hardware, for move / click / drag.

Plain hjkl movement does no scanning at all, which is what keeps it feeling instant: the expensive capture-and-OCR only happens when you actually ask for hints.

Honest about what's proven

The journal is deliberately clear about what is runtime-tested against a real display versus what is structurally correct but needs hardware to prove out — and where to take it next (Wayland is the obvious frontier, since the X11 overlay and synthetic-input tricks don't translate directly).

Module map, phase-by-phase build, dependency choices and the tested-vs-needs-a-display breakdown are all in JOURNEY.md.
